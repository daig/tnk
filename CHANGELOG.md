# Changelog

All notable user-visible changes are documented here. This project follows Semantic Versioning for release identifiers; compatibility guarantees are qualified by the feature states in the normative reference.

## [Unreleased]

### Added

- Added immutable host-function catalogs and strict Rust reducers: source operators can bind typed or scoped in-process callbacks through `HostFunctionSymbol`, with eager argument normalization, build-time strategy/hook validation, equation fallthrough, checked result normalization, structured tracing/accounting, and fault propagation across Session, reflection, child-interpreter, rewrite, search, variant, and narrowing paths.

- Added catalog-aware Session, frontend, module, reflection, and low-level Engine construction paths. Catalogs survive module sums, views, parameter instantiation, renaming, dependent rebuilds, and nested execution without process-global registration or live callback replacement.

### Correctness and hardening

- Scoped callback DAG wrappers and callback-lifetime `HostSymbol` capabilities prevent raw engine-handle escape, captured or cross-engine callback construction, reentrant reduction, and unsafe collection. Host bindings are sealed before semantic execution; missing capabilities and incompatible eager schedules, overloads, sorts, theories, or supporting hooks reject module construction.

- Cyclic subsort declarations, including self-loops and cycles formed only through imports, are now rejected with an ordinary `error:` module diagnostic instead of panicking (the CLI previously exited with status `101`). The invalid module is not installed and the Session continues. `Sorts::subsort_cycle` and `Engine::subsort_cycle` expose the check to low-level callers.

- `modExp(B, E, M)` now reduces to `B^E mod M` for every natural base, including a base at or above the modulus and any base with modulus `1`, instead of panicking (the CLI previously exited with status `101` and printed nothing for the whole submission). This also covers `metaReduce` of such terms. A zero modulus still leaves the term unreduced.

- The CONVERSION built-ins no longer read the kind-level `I / 0` that the division built-in leaves unreduced as a rational: `float(I / 0)` now stays unreduced instead of panicking, and `string(I / 0, B)` stays unreduced instead of producing the invented string `"I/0"`. `rat(S, B)` likewise falls through when the denominator in `S` is negative, instead of dropping its sign (`rat("3/-2", 10)` gave `3/2`).

- `irredundant unify`, `metaIrredundantUnify`, and variant generation (for example `get variants`) no longer panic when a binding under an operator with a one-sided identity contains an `iter` count of `2^64` or more; the redundancy filter now keeps the arbitrary-precision count.

- `find`, `rfind`, and `substr` now reduce when an index or count argument is `2^64` or more. The answer is the same as for any other position past the end of the string: `notFound` for `find`, the last occurrence for `rfind`, and a clamped slice for `substr`. These applications previously stayed unreduced, so for example `find("ab", "b", 18446744073709551616) == notFound` gave `false`.

- `_^_`, `_<<_`, and `_>>_` now reduce for an exponent or shift count of `2^64` or more whenever the exact result is small: `0 ^ N`, `1 ^ N`, `(-1) ^ N` (by parity), `0 << N`, and `I >> N` (`0`, or `-1` for a negative `I`). Previously these applications stayed unreduced, so `1 ^ 18446744073709551616 == 1` gave `false`. Any other base, and any nonzero value shifted left, still stays unreduced for such counts. A negative shift count lies outside `_<<_`/`_>>_ : Int Nat -> Int`, so the application now stays unreduced, as one with a negative exponent already does. Previously it shifted by the count's magnitude: `7 >> -1` gave `3`.

- `I ^ N` no longer returns a wrong value, panics, or aborts when `N` fits 64 bits but the power's size bound, the bit length of `|I|` times `N`, overflows 64 bits (such a power has more than `2^63` bits). In these cases the numeric backend's unchecked size arithmetic wrapped: `2 ^ 9223372036854775808` reduced to `1`, `7 ^ 6148914691236517206` panicked (the CLI exited with status `101`), and `3 ^ 18446744073709551615` aborted. Both crashes lost the whole submission's output. Such a power now stays unreduced, as one with an exponent of `2^64` or more already did. Other powers too large to allocate, such as `3 ^ 9223372036854775807`, are unchanged by this fix.

- Each `CounterSymbol` operator now has its own `0, 1, 2, ...` sequence. Previously all counter operators in a module drew from one shared value. This affected two directly declared counters as well as a renamed copy such as `COUNTER * (op counter to counter2)`. With such a copy, `rewrite counter counter2 counter counter2 .` gave `0 1 2 3` instead of `0 0 1 1`, and in a fresh `rewrite counter2 counter2 counter .` the `counter` gave `2` instead of `0`. The fix applies to `rewrite`, `frewrite`, `erewrite`, `continue`, `metaRewrite`, and `metaFrewrite`. All counters still restart at `0` for each top-level rewriting command. Modules with a single counter operator are unaffected.

- Within one statement or command, a variable is now identified by its written name and resolved sort. A declared `X : S` and an on-the-fly `X:S` are therefore one variable, and so are the kind spellings `X:[A]` and `X:[B]` of one kind. Previously each spelling got its own slot, but the unifier treated them as one, which caused four failures:
  - `unify` and `metaUnify` could return unsound unifiers;
  - `match`, `search`, variant, and narrowing commands bound the spellings independently;
  - equations such as `eq g(X) = X:S` were dropped as having an unbound right-hand-side variable;
  - a `search` condition that named the goal variable by its other spelling panicked.

  A matchrew `by` variable may now use any spelling of a pattern variable. Object-pattern completion no longer reuses a written `V:Class` as its fresh class variable.

- A nullary operator spelled as a literal token that the module also reads as a literal (for example `op "hi" : -> Foo` beside `STRING`, `op 'a : -> Foo` beside `QID`, or `op 42 : -> Foo` beside `NAT`) now prints as `(c).Sort` in results, substitution bindings, `metaPrettyPrint`, and the reduce, rewrite, and search command echoes whenever context does not fix its range. A string, quoted-identifier, or float literal whose value such an operator spells is qualified the same way, the top level included. Previously both printed bare, so the text reparsed as the other term or was rejected as ambiguous where a unique parse is required (`TNK-OUT-002`). The zero constant `0` and spellings that no literal production of the module accepts still print bare.

- A term whose least sort is its kind's error sort and that needs a range qualifier (a `poly` range instance, a `~>` or `[K]`-range operator, or an overload applied outside its declared domain) now prints as `(t).S` with a user sort `S` of its kind, for example `(f(a2)).B` instead of `(f(a2)).[B]`; the `(t).[K]` form is rejected by tnk's own parser (`TNK-OUT-002`). This applies to results, command echoes, and META-LEVEL `with-sorts` printing; the `result [K]:` header still names the kind. META down-translation likewise qualifies a kind-level identity element such as `` id('e.`[Foo`]) `` with a user sort, so such a meta-module now builds instead of failing.

- A single application of an `iter` operator now prints like any other application of an overloaded operator. When a same-name operator shares its domain kind, it prints `(h(a)).Foo` instead of a bare `h(a)` that reparsed as the other operator; when the operator is ad-hoc overloaded and context does not fix its range, its argument keeps its qualifier (`p((o).N)` instead of `p(o)`) (`TNK-OUT-002`).

- When two `iter` operators share a name (necessarily in different kinds), the argument of their compact `h^N(t)` form keeps its qualifier unless context fixes the range: `h^2((c).Bar)` instead of `h^2(c)`, which reparsed in the other kind (`TNK-OUT-002`).

- A colon variable spelled with the printed name of a kind that has several maximal sorts, such as `X:[B,A]`, now parses as a variable of that kind. Generated variables print in this form (`#1:[B,A]` in unifiers and variants), which previously failed with `no parse` when fed back (`TNK-OUT-002`). Other multi-sort bracket lists, such as `X:[A,B]`, are still rejected; `X:[S]` with one sort of the kind is unchanged.

- An executable equation whose whole left-hand side is a variable (plain, conditional, `owise`, or `variant`; in a module or theory; or an instance equation that a view maps to a variable) is now dropped with a `dropped equation: equation left-hand side is a variable` warning, like the existing membership and rule cases, instead of panicking (the CLI previously exited with status `101` and lost the whole file's output). Reflected modules containing an executable equation, membership, or rule of this shape no longer panic or silently ignore the statement: they do not down-translate, so metalevel descent stays inert (except `getKinds`, which reads only the sort signature), `wellFormed` returns `false`, and `insertModule` receives an interpreter error. `[nonexec]` statements and `[narrowing]` rules are unchanged. Whether such statements should execute is undecided; Appendix H.4.1 and K.3 of the reference record the current boundary.

- An imported statement that its home module rejects at the statement boundary (unbound variable, variable left-hand side, rewrite condition outside a rule, or conditional narrowing rule) is no longer reparsed in the importer's grammar. Previously an importer declaration, such as a constant named like the home variable, could silently install a different statement in the importer.

- Reflected modules now get the source loader's unbound-variable and rewrite-condition checks. Metalevel descent used to install, as is, an executable statement with a right-side or condition variable that neither its left side nor an earlier `:=` or `=>` fragment binds (executable `[narrowing]` rules included), and an equation or membership with a rewrite (`=>`) condition. Installing the latter, or applying the former, panicked (the CLI exited with status `101`); otherwise the statement was used where the source loader would have dropped it, for example by `metaApply` with a substitution or by `metaNarrowingApply`. Such a module value now does not down-translate, like one with a variable left-hand side: metalevel descent stays inert (except `getKinds`), `wellFormed` returns `false`, and `insertModule` receives an interpreter error. `[nonexec]` statements are unchanged, so a reflected rule with a fresh right-side variable still descends as `[nonexec]` and is used for narrowing as `[nonexec narrowing]`, as at the source level.

- Object-pattern completion no longer completes a statement that changes an object's class. When the left-side class was a constant, its fresh class variable replaced the class argument of every right-side and condition occurrence of that object: `< O : Open | bal : N > => < O : Closed | bal : N >` kept the class `Open`, a class carried in a message was ignored, a condition about another class tested the matched class, and a rule with an unbound right-side class variable became executable. When the left-side class was a variable, the shared attribute-set variable carried the matched object's other attributes into the new class. Such statements are now left exactly as written (`TNK-OO-002`), so an executable statement with an unbound right-side class variable is dropped with a warning. This is an incompatible change to Experimental object-module desugaring: class-changing statements, including those written with a left-side class variable, no longer match objects that carry attributes beyond the written ones, and a left-side class constant in such a statement no longer matches subclass objects.

- Object-pattern completion no longer treats an `Attribute`-sorted constant or a non-unary `Attribute`-ranged operator in the attribute set of a left-side object pattern, or of another occurrence of that object, as an attribute. An element such as `flag` that occurred only on the right side was added to the left side as the one-argument term `flag(A:[AttributeSet])`, so the rule could never fire and up-translating the module with `upModule` panicked on an arity assertion (the CLI exited with status `101`); an element on the left side was copied back to the right side, so a rule could not remove it. Such statements are now left exactly as written (`TNK-OO-002`). As with class-changing statements, those that were completed before no longer match objects that carry additional attributes, nor, when written with a class constant, subclass objects.

- Object-pattern completion now chooses fresh variable names that differ from the base name of every variable in the statement. It compared candidates with whole source tokens, so beside a user `V:C` or `Atts:AttributeSet` it introduced another `V:C` or `Atts:AttributeSet`. The verbose completion transcript and `upModule` then showed the two variables as one, and a module rebuilt from the reflected text required them to be equal. The fresh names are now `V2`, `Atts2`, and so on in such statements (`TNK-OO-002`).

- Entering a module with an executable `[narrowing]` rule no longer panics when one of the rule's variables has a base name that never occurs as a token of its own (the CLI previously exited with status `101` and lost the submission's output). The lexer reads an on-the-fly variable such as `Zqx:S` as one token, and object-pattern completion introduces variables such as `Atts` or `V2`, so such a module loaded only when each base name happened to occur elsewhere, for example in a variable declaration or the prelude. Preparing the rule's narrowing trace now interns the base name, as the narrowing commands already do for their own variables.

- Object-pattern completion now follows a statement declared by an object module or theory into every module that imports it. Completion was decided by the root of the flattened import closure, so a `mod` that imported an `omod` directly, transitively, renamed, or instantiated, a parameterized `mod` whose parameter theory is an `oth`, and a reflected module including an `omod` ran the object module's statements as written: they no longer matched subclass objects or objects carrying attributes the statement does not mention, and flat reflection showed them uncompleted. Reduction, rewriting, search, and narrowing in such importers can therefore now apply statements that they did not apply before. An object module still completes the object-syntax statements it imports from plain modules; whether it should is left unspecified (`TNK-OO-002`).

- `upModule`, `upRls`, `upEqs`, and `upMbs` now reflect the `[nonexec]` rules, equations, and memberships of an object module in completed form, as they already reflected its executable statements; flat reflection does the same for the object-module statements an importer inherits. Reflection re-parsed nonexec statements without object-pattern completion, so the reflected module disagreed with the module it reflects: the module's own narrowing and SMT rule tables hold the completed `[nonexec narrowing]` rules, and a module rebuilt from the reflected statements narrowed differently, for example failing on an object that carries an attribute the rule does not mention (`TNK-OO-002`).

- A CUI identity-collapse rewrite that matches one argument of a non-commutative `[id: e]` operator now leaves the rewritten argument in its own position. With `eq t(A) # e = k(A)`, `red b # t(a)` now gives `b # k(a)`. It previously gave `k(a) # b`, a term not equal to the input modulo the operator's axioms. Commutative operators are unaffected.

- CUI matching at a subject rooted at the operator now also returns the collapse matchers, after the ordinary pairings. Under `[id: e]`, one pattern operand can take the whole subject and the other the identity, so `match f(X, Y) <=? f(a, b)` returns 3 matchers (4 with `comm`), the same solutions the CUI unifier returns. Under `[idem]`, both operands can take the whole subject. As a result, `eq f(f(A, B), e) = h(A, B)` now rewrites a top-level `f(a, b)`. Rules, strategies, and reflection see the new matchers as well. For `rl f(X, Y) => g(X, Y)`, `search` and `srew` report the extra one-step successors `g(f(a, b), e)` and `g(e, f(a, b))`. `metaMatch`, `metaApply`, `metaSearch`, `metaXmatch`, and `metaXapply` return the new solutions too, and solutions enumerated after them (for example matches at argument positions) move to higher indices. A rule set that is non-terminating modulo the identity, as this one is, now has an infinite search space where it previously had a finite one.

- `metaXmatch` and `metaXapply` no longer report one solution per copy of a repeated element of an associative-commutative subterm. With `rl d => c`, `metaXapply` over `'__['d.Coin, 'd.Coin, 'd.Coin]` returned the same 4-tuple at indices 0, 1, and 2; index 1 now returns `failure`, and `metaXmatch` of `'d.Coin` likewise returns `noMatch` at index 1. A meta-program that counts one-step rewrites by increasing the index until failure therefore counts the copies once, and solutions after a repeated element move to lower indices. Equal arguments of every other operator, including commutative ones, remain separate positions.

- Narrowing (`vu-narrow`, `fvu-narrow`, `metaNarrowingSearch`, and `metaNarrowingApply`) now explores both arguments of a free, associative, or non-commutative identity/idempotent operator when they are one shared subterm. This sharing arises when a rule instance repeats a variable, as in `rl h(Y) => f(Y, Y)`, and in ground subjects such as `f(g(a), g(a))`. The second argument was previously skipped while exhaustion was still reported complete: with `rl g(a) => c`, `vu-narrow h(g(X)) =>* f(g(a), c)` answered `No solution.`, and `vu-narrow f(g(a), g(a)) =>1 Z` found only `f(c, g(a))`. Both now find `f(g(a), c)`, so solution and rewrite counts grow where such sharing occurs, and a state with heavily shared subterms can have many more positions to explore. Commutative operators are unchanged: two equal arguments that are one shared subterm are narrowed once, because both choices give the same states modulo commutativity. A repeated element of an associative-commutative operator is still one position, now also when its copies are separately built equal subterms.

- An `=>*` `smt-search` or `metaSmtSearch` now reports its initial state only when the SMT backend returns `Sat` for the `such that` constraint, as for every other state and goal match. The backend's answer for the initial constraint was ignored, so the initial state was checked only through the goal's own SMT match constraint. A goal without SMT-sorted variables therefore matched unchecked: `smt-search f(J) =>* X such that J = J + 1 .` reported Solution 1 `where J === J + 1`, and `metaSmtSearch` returned that state as solution 0. A configured backend also kept a match whose initial constraint it could not translate (`BadDag`), because the match constraint was then checked alone. Under the default null backend, which answers `Unknown`, an `=>*` search with a non-trivial `such that` constraint no longer reports its initial state. Searches without one are unchanged, because the literal `true` constraint, which the null backend also answers `Unknown`, stays exempt from the check. That exemption is provisional until trivial constraints are decided.

- A rule step below an `iter` operator now keeps the operator's iteration count. Rebuilding the rewritten term re-wrapped each `iter` ancestor `f^n(...)` as the single application `f(...)`, so with `rl a => b`, `rew s_^3(a)` gave `s b` instead of `s_^3(b)`, and with the prelude's `Nat` successor, `rl a => 0` made `rew s_^3(a)` give `1` instead of `3`. The same loss affected `frewrite`, `erewrite` outside a configuration, `search` and its goals (`search s_^3(a) =>* s_^3(b)` found nothing), rewrite conditions, LTL model checking (which could return the wrong verdict), strategy rule application and `amatchrew`, and `metaRewrite`, `metaFrewrite`, `metaSearch`, and `metaXapply`. A rewritten argument that is itself an application of the same `iter` operator folds into the count, so `rl a => s a` takes `s_^3(a)` to `s_^4(a)`. The contexts that `metaXapply`, `metaXmatch`, `metaNarrowingApply`, and `metaNarrowingSearchPath` return now also head an `iter` ancestor with its count, `'s_^3[[]]` instead of `'s_[[]]`, so they agree with the reflected result term.

- `ops` and `msgs` now treat each top-level parenthesized group as one operator name with its quoting parentheses removed, so `ops (m{X}) (n{X}) : -> S .` and `ops (_+_) (_*_) : S S -> S .` declare the intended operators. Previously every token was declared separately, including operators named `(`, `)`, `{`, `}`, and `,`, and statements using the intended names were dropped. The grouped names also instantiate as parameterized and `[pconst]` constants. An empty group or an unmatched `)` in the name list is now a parse error.

- Renaming items now accept parameterized class and message names: `class Foo{X} to Bar{X}` reads both classes as sort names, as class declarations and view class maps do, and `msg m{X} to n{X}` reads structured message names. Both were parse errors, so the importing module was not installed. Because class names in renaming items are now read as sort names, a class name containing `.` on either side is now rejected, as in `sort` renamings.

- The documented class-qualified attribute maps `attr a . C to b` (renaming item) and `attr a . C to b .` (view map) are now accepted, including a structured class such as `Buf{X}`. Both were always rejected with ``expected `to` ``, because a period before an ordinary word is not a terminator token (`TNK-LEX-001`). The qualifier does not narrow the map: attribute operators are shared by name across classes, so `attr a . C to b` also maps attribute `a` of every other class, exactly like `attr a to b`.

- Condition fragments whose terms contain connective spellings are now kept, as in object syntax `< O : C | > = < O : C | >`, a user `<_:_>` operator, or a Boolean term `< X : t > == < a : t >`. Each fragment was split at its first `:=`, `=>`, `=`, or `:` token, so the object's own `:` became a sort test and the valid `ceq`, `cmb`, or `crl` was dropped as "no parse"; a `search`, `smt-search`, or `matchrew` `such that` condition was rejected the same way. The first token's split still wins whenever it builds, so conditions accepted before keep their meaning. Otherwise a fragment needs exactly one reading among its later connective tokens and the whole fragment as a Boolean term; several readings drop the statement as an ambiguous condition fragment. Object-module rules kept this way now reach object completion. Some invalid conditions with such terms now report their actual problem, such as a rewrite fragment in an equation or an unbound variable, instead of a no-parse of the object's prefix.

- A membership whose subject contains a colon is now kept, as in `mb < e : t > : S2 .` or an object pattern `mb < O : Cell | val : v > : Good .`. The first colon was taken as the membership delimiter, so the statement was dropped, and a subject containing `: Name [`, as in `< e : t [ a ] >`, rejected the whole module. The delimiter is now the first colon followed only by a sort name and an optional attribute group (`mb`), or by a sort name and `if` (`cmb`). An unknown target sort after such a subject is now reported as an unknown sort.

- `ceq` and `crl` statements with an unparenthesized `if_then_else_fi` beside the condition keyword are now kept. The first top-level `if` was taken as the condition keyword, so an `if ... fi` right side dropped the statement, and an `if ... fi` left side of a `ceq` rejected the whole module with ``equation is missing `=` ``. Top-level `if` and `fi` tokens now pair like brackets, and the condition keyword is the first `if` that no later `fi` closes.

- Parse errors now name the found token by its source text, as in ``expected a name, found `.` `` or ``expected `is`, found `sort` ``, or say `found end of input`. They printed an internal Rust representation instead, such as `Some(Token { sym: Sym(9), line: 2, kind: Dot })`, `Some("sort")`, or `None`. A missing name, as after a dangling `+` in an import, is now reported at the offending token's own line and inside its enclosing module or view. The line of the following token was reported, and the module or view was omitted when that token closed it. A `.` terminator where a module or view name belongs is no longer reported as a module named `.`.

- Skipping unrecognized top-level tokens and source `set` directives no longer uses a stack frame per skipped token. A long unrecognized statement, or a long run of them, could abort a debug build with a stack overflow after a few hundred skipped tokens, or fewer on a thread with a smaller stack, losing all output of the submission. Release builds were protected only by an optimization that Rust does not guarantee. The skip is still silent (Reference H.4.1).

- Strategy branches now follow `TNK-STRAT-002`. `T ? S : F`, `or-else`, and `try` run their success arm on every solution of the test, not only the first. `try(E)` keeps the unchanged subject when `E` has no solution; it used to fail. `test(E)` returns the unchanged subject once; it used to return `E`'s first rewritten result. These are behavior changes:
  - Normalizing over `try`, as in `try(E) !`, has no normal form, because `try` never fails.
  - A branch, `try`, or `or-else` whose test has infinitely many solutions now diverges under the eager `srewrite` and `dsrewrite` commands. It used to return a truncated result.
  - A recursive definition such as `sd loop := step ? loop : idle` follows every solution of `step`, which can take exponentially longer.
  - `one(T) ? S : F` keeps only the first test solution, as `T ? S : F` used to.

- A committed `one`, `not`, or `test` now discards its whole remaining sub-search, including nested named-call bodies, branches, `one` sub-searches, and normalizations. These nested tasks used to keep running after the commit, so `one(s)`, `not(s)`, or `test(s)` with `sd s := r *` over an infinite `r *` never finished, although the inlined `one(r *)` did.

- `matchrew` and `amatchrew` `using` strategies now see the variables bound by the pattern and by `:=` fragments of the `such that` condition, with the match's values before rewriting (`TNK-STRAT-002`). A `using` strategy that mentions any other condition variable, for example one that only an equality fragment mentions, is now rejected. A reflected strategy rewrite of a non-ground term is rejected when such a strategy uses a variable bound to a non-ground subterm. Such a variable used to be out of scope:
  - In a strategy-call argument or a `[V <- t]` value, the command was rejected as using an unbound variable.
  - In a nested pattern or condition, it was a fresh variable, so the command gave wrong results.
  - In a strategy definition, the definition was silently dropped, so its calls answered `No solution.`.

- A `matchrew` `by` variable must be a distinct variable of the pattern. A `by` variable that occurred only in the condition used to panic (equality fragment) or silently discard its substrategy's result (`:=` fragment). A repeated one kept only the last substrategy's result. Both are now rejected.

- A `matchrew` `by` variable that the enclosing strategy definition or matchrew already binds is matched at that value, and its occurrences are rebuilt from the substrategy results. Such a variable used to panic.

- `matchrew` and `amatchrew` `using` strategies, and the condition substrategies of a rule application such as `lift{S}`, now run as child searches of the strategy command (`TNK-STRAT-001`). They used to run to completion before any result was combined, so an infinite one never let the command finish, even under `one`, `not`, or `test`, and it starved every fair `srewrite` sibling. A match is now rebuilt as soon as each of its by-variables has a result, and a conditional rule rewrites as soon as its condition has a solution. For example, `one(matchrew f(X:S) by X:S using r *)` and `one(lift{r *})` now finish. Behavior changes:
  - Under `srewrite`, results follow the fair order across matches and condition solutions, so their order can change and `one(...)` can keep a different result: the first one to complete.
  - Per-solution rewrite counts can change.
  - Under `dsrewrite`, an infinite search for an earlier `matchrew` by-variable still prevents any result, because depth-first exploration does not reach the later by-variables.

- A strategy that recurses through `matchrew` by-variables or rewrite-condition substrategies no longer overflows the native stack. From about 5,000 levels such recursion aborted the process with a stack overflow (exit status `134`), and all output of the input was lost. These nested sub-searches now live in the command's task tree, and abandoning a deep failed nest, including a deep chain of named calls, is a loop rather than native recursion.

- Rejected Session requests now start with the Stable `error:` severity prefix (`TNK-OUT-001`). This covers unknown `show` forms; `show` inspections with no current module or an absent module, view, search graph, narrowing graph, or state; failed `select`; malformed `set trace` requests; `continue` without a usable continuation; and commands entered with no current module. The two narrowing displays no longer print a capitalized `Warning:`, and `show module NAME .` for a missing module no longer claims that no module is current. Clients that detect diagnostics by prefix now see these rejections. Their state effects are unchanged.

- `load FILE .` and `sload FILE .` now remove the optional final command dot from the path, as Appendix D specifies. They previously searched for a file named `FILE .` and failed with `cannot open file`. A `.` glued to the name (`load FILE.`) is still part of the path, and `load .` now reports that a file name is missing.

- An `smt-search` request rejected while the command is built now reports an `error:` diagnostic instead of printing nothing. This covers the unsupported `=>!` mode, a module or goal outside the restrictions for rewriting modulo SMT, and a `such that` condition that does not parse or is not supported. As before, the rejected request prints no command echo and creates no search or continuation.

- `show modules .` now lists each built module once, in entry order. A dependent dropped because its rebuild failed after a redefinition is no longer listed, matching `select` and `show module`, which already reported it missing. Entering it again lists it once, at the end, instead of twice.

- Operator renamings and view operator maps now rewrite each statement term, identity attribute, and term hook once, from its source parse. A mixfix map such as `op _,_ to _;_` also rewrote the argument commas of prefix applications (`insert(E, S)` became a one-argument application). As a result the stock prelude's META-VIEW, META-MODULE, and META-LEVEL, and every module importing them, dropped the 15 equations of the renamed `QID-SET` (`insert`, `delete`, `|_|`, `union`, `intersection`, `_\_`, and their helpers) with `dropped equation: no parse`, and a corrupted equation whose text still parsed silently became a different equation. Instantiating a parameterized module through a view with such a map had the same defect: the instance dropped an equation such as `eq pair(A, B) = A, B`. The same change fixes swapped or chained renamings (`op f to g, op g to f` was applied twice) and profile-qualified renamings that also renamed a same-name, same-arity overload in another kind. A term whose source parse is ambiguous because an operator is overloaded across kinds, in a renamed module or in an instance, is no longer rewritten token by token: it is rebuilt when the readings agree and kept unchanged otherwise.

- A renaming or view operator map whose source is the juxtaposition operator (`op __ to _;_`) no longer rewrites arbitrary pairs of adjacent tokens. Previously every multi-token statement copied through such a renaming (including imported ones such as BOOL's connectives and LIST's equations) or instantiated through such a view was corrupted and dropped with `dropped equation: no parse`.

- Operator renamings and view operator maps now apply inside conditions. Each term of an equation, membership, rule, or strategy condition (a side of `=`, `:=`, or `=>`, the subject of a sort test, or a bare Boolean fragment) is rebuilt from its source parse like any other statement term. Previously a condition kept a mixfix or profile-qualified operator under its source spelling: after `op _+_ to _*_`, a statement such as `ceq f(X) = c if X + X = b` was dropped with `dropped equation: no parse`, and when the old spelling still named an operator of the renamed module (as in a swap) the condition silently tested that other operator. A strategy `match … such that` or `matchrew … such that` test silently found no solution. Instantiation through a view map that changes fixity (`op lt to _<<_`) had the same defect in the instance's conditions.

- A profile-qualified operator renaming (`op f : Foo -> Foo to g`) now renames the whole overload family its profile names: every declaration of that name and arity whose sorts lie in the profile's kinds, together with the statements and `op-hook` references that use the family. Previously only the declaration spelled exactly like the profile was renamed while the statements moved with the family, so a subsort-overloaded family was split: with `Foo < Bar`, the renamed module kept `f : Bar -> Bar` beside `g : Foo -> Foo`, and the family's equations applied to `g` only at the kind level. Renaming INT's `-_` family through one profile failed with ``operator `$neg` uses `ditto` without a preceding declaration of the same arity``, and `op _+_ : Int Int -> Int to $add` left `_+_` on the naturals. For the family it selects, a profile-qualified map now also takes precedence over a plain map of the same name in declarations and `op-hook` references (including those a view map rewrites), as it already did in statements; previously the first matching item won, and in a renaming the statements of that family were then dropped. A source that renamed only one member of a subsort-overloaded family now renames the whole family.

- A plain-imported equation or rule is now reparsed in its home grammar with its right side in its left side's kind, as in the flattened grammar. A right side that is a constant overloaded across kinds (such as META-MODULE's `getRls(...) = none`) was ambiguous there, so the statement fell back to the importer's grammar. An importer variable spelled like a home variable then dropped the statement or silently changed its sort; for example, `vars SS ST : String` in a module including META-LEVEL dropped ten getRls/getStrats/getSds equations.

- Statements and strategy definitions donated through a renamed import (`M * (...)`, `(M * R){V}`) or a parameter copy now keep their home module's variable declarations. Such statements parse in the importer's grammar, where the importer's own variables, or an earlier import's variable of the same name, used to re-bind their bare variables, dropping the statement or silently changing its sort. For example, nine BOOL-OPS equations were dropped in each of the stock WEAKLY-SORTABLE-LIST and WEAKLY-SORTABLE-LIST', and a parameterized module declaring its own `A`, `B`, or `C` at another sort dropped the BOOL-OPS equations using that name. Exactly the variables the importer would bind differently are now inlined as colon variables at their home sort; the others keep their spelling. A variable spelled like a constant the renaming introduces (`var m` under `op n to m`) is inlined before renaming, so the constant keeps its meaning. Inlining is lexical. Take a home with `var s` and `op s_`, imported this way by a module that declares its own `s`. A home statement applying that operator, such as `h(s z) = z`, is now dropped (see TNK-DEV-003).

- A `,` in a module or view `var`/`vars` name list now only separates names: `vars W, X : S .` declares `W` and `X` and no longer also declares `,` as a variable. The declared `,` was rewritten as a variable wherever composition rewrites statement tokens by name, so instantiated statements and statements whose `,` collided with an imported one at another sort were dropped (`no parse at token … (,:S)`), and instantiated strategy match patterns silently found no solution. A view with such a list also rejected a mixfix source like `op { X , Y } to term …` (`source operator {___}`), and `upView` of such a view stayed unreduced. A statement that uses `,` itself as a variable term no longer parses.

- Instantiation now rewrites every component of a multi-sort kind spelling: under `V` mapping `Elt` to `Hue`, `[S{X},T{X}]` becomes `[S{V},T{V}]` and `[X$Elt,S{X}]` becomes `[Hue,S{V}]`. The bracket text used to be instantiated as one sort name, so such an instance was rejected (`unknown sort S{X} in kind [S{X},T{X}]`). The kind-spelled profile sorts of an instantiated renamed module `(M * R){V}` get the same per-component parameter substitution.

- View operator-map selectors may spell their sorts as kinds (`op f : [Elt] -> [Elt] to g`), as the `OpSelector` grammar allows. Such a view used to be rejected (`source operator f is not defined`); it now validates, and an instantiation qualifies the selector's theory sorts (`[X$Elt]`) and applies the map to the overload declared at that kind. An instantiation still requires an operator declared at the selector's kind: a view whose kind selector names a sort-declared operator installs, but instantiating it reports `source operator … is not defined`. Operator renamings still reject kind-spelled profiles.

- A view variable may be declared at a kind (`var Z : [Elt]`) for an operator-to-term map; it takes the kind of its sort image in the target. It used to be rejected (`variable sort [Elt] is not a source theory sort`).

- A chained instantiation `M{V}{Y}` that passes an enclosing parameter `Y` straight after a theory view `V`, inside `fmod M2{Y :: T2}` with `V` from `T` to `T2`, now names the view's images as in `Y`'s parameter copy of `T2`. Mapped and identity-mapped sorts become `Y$s` (sorts that `T2` imports from ordinary modules stay shared), and `T2`'s parameter constants become `Y$c` in plain, profile-qualified, identity, and operator-to-term maps. Previously the instance named such a sort `Y$Foo` after the source sort (an `unknown sort` error, so the module was not installed) unless the view mapped it to a same-named sort declared by `T2` itself, and it did not rename parameter constants into `Y`'s copy, so statements using them were dropped. A longer chain ending in `Y` gets the same names only when no view after its first maps operators; otherwise it keeps the previous behavior, because the views' operator maps are merged rather than composed.

- The dependents of a redefined module or view are now rebuilt imports first, so each rebuilt dependent equals a fresh build of its source. A rebuild reparses imported statements and strategy definitions in their home modules' grammars, taken from the cached builds, but dependents were rebuilt in an arbitrary order that changed from run to run. A dependent rebuilt before one of its homes kept that home's pre-redefinition parse. For example, an equation could keep an operator precedence that no longer existed, or an imported strategy's `match` pattern could stop matching. The failures of a dependent rebuild are now also reported in the same order on every run.

- A module and a view with the same name now keep separate dependency records. Identity views named after their targets are one example, such as the stock prelude's `view TRIV from TRIV to TRIV`. Before, the later definition replaced the other's record, so a redefinition could skip rebuilding a dependent, which then kept running against the replaced definition. This hit the importers of a module sharing a view's name, the users of a view sharing a module's name, and a module instantiated with a view of its own name. It also hit a theory named like its identity view, together with the modules parameterized by that theory. `tnk_modules::load::{DepRef, module_dep_refs, view_dep_refs}` replace the bare-name `module_dep_names` and `view_dep_names`.

- A dependent rebuilt after a module or view redefinition now reports the statements it drops, as a direct definition does. Rebuilds used to discard these diagnostics, so a redefinition that broke an importer's equation, membership, or rule removed it without any output. A warning still appears once while the drop persists. It is now forgotten once no built module produces it, so a recurring drop is reported again. This includes a drop that only an importer's grammar produces, whether the importer is rebuilt or entered again.

### Documentation

- `TNK-STRAT-001` and `TNK-STRAT-002` now state that `matchrew` by-variable strategies and rule-application condition substrategies are child tasks of the command's schedule, when a match is rebuilt or a conditional rule rewrites, and that `dsrewrite` explores the by-variables in order.

## [0.1.0] - 2026-07-29

Initial supported release of tambanokano.

### Added

- Order-sorted signatures with kinds, subsorts, overload resolution, memberships, partial operators, and free, AU, ACU, and CUI canonical term representations.
- Equation reduction, conditional rewriting, fair rewriting, breadth-first reachability search, saved continuations, search graph inspection, and path reconstruction.
- A strategy engine with fair and depth-first scheduling, combinators, rule applications, tests, match-rewrite, and lazy recursive parameterized strategy calls.
- Order-sorted unification, irredundant unifier filtering, variants, variant unification and matching, narrowing, variant satisfiability, and explicit incompleteness outcomes.
- Native LTL model checking and satisfiability, a default null SMT backend, and an optional Z3 backend behind `smt-z3`.
- Module and view databases with imports, sums, structural renaming, parameter instantiation, dependent rebuilds, import hygiene checks, and transactional definition failure.
- Object-module desugaring, external stream objects, interpreter-manager objects, metalevel command descent, module/term reflection, and child interpreter state.
- Reusable `tnk-core`, `tnk-frontend`, `tnk-modules`, and `tnk-session` APIs plus the interactive `tnk-repl` executable.
- A documentation suite comprising the normative language and system Reference, a guided TNK Book, and a compact Quick Reference for syntax, commands, controls, and modeling gotchas.

### Correctness and hardening

- Preserved DAG roots across GC-capable reduction, matching, unification, strategy, reflection, and condition-evaluation paths; engine-relative handles now fail fast when used with the wrong engine.
- Made deeply nested condition evaluation heap-growing rather than dependent on the native call-stack limit.
- Enforced declaration-group kind coherence, least-sort selection, safe fresh-variable families, unsupported-theory screening, import-cycle rejection, and free-parameter import rejection.
- Kept rewrite counts, continuation state, module selection, source diagnostics, and failed-definition rollback consistent across direct, imported, renamed, instantiated, and reflected modules.
- Made recursive parameterized strategy definitions runtime-lazy, removing any resolution-time expansion bound.
- Added strict CLI argument parsing: unknown flags and extra files exit with status 2; unreadable requested files exit with status 1; evaluation diagnostics remain session output.
- Hardened differential tooling against timeouts, missing binaries and libraries, subprocess failures, stale expected output, and shell word-splitting of library paths.

- Added deterministic unit and integration coverage across every workspace layer, including behavioral boundary tests for parsers, continuations, GC safety, unsupported unification, metalevel caches, object systems, and CLI process behavior.
- Added retained conformance fixtures for the supported source language, prelude surfaces, strategies, modules/views, reflection, SMT, LTL, objects, variants, narrowing, and recursive parameterized strategy calls.
